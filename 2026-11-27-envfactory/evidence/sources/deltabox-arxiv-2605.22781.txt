 Abstract.

 Emerging LLM-powered AI agent workloads, such as test-time tree search and reinforcement learning (RL), require high-frequency state exploration, relying on rapid checkpoint/restore (C/R) of the complete sandbox state, including files and process state.
Existing mechanisms duplicate the entire state, causing hundreds of milliseconds to seconds of latency per C/R, which severely bottlenecks deep search and large-scale fan-outs.

 We observe that consecutive sandbox states between checkpoints differ only marginally.
Therefore, instead of full duplication, a sandbox should only duplicate the changes between consecutive checkpoints ( Key Insight ), yet the lack of OS support makes this hard to realize.
We propose a new OS-level abstraction, DeltaState , that delivers change-based C/R for agents through co-designed OS mechanisms.
First, DeltaFS checkpoints file state by freezing the writable layer and inserting a new one, turning updates into copy-on-write and rollback into a layer switch.
Second, DeltaCR quickly restores process state by forking from a frozen template process. A coordinator pairs the two so each checkpoint is one consistent (filesystem, memory) state.
Building on these mechanisms, we present DeltaBox, an agent sandbox with millisecond-level C/R.
On SWE-bench, DeltaBox hides its checkpoint work (10.83 ms) under inference and rolls back in a mean 1.86 ms, with the same warm-template fork driving low-cost RL rollout fan-out.
DeltaBox is open-sourced at https://github.com/delta-box .

 1. Introduction

 LLM-powered agents now automate complex, multi-step tasks, from code repair ( Jimenez et al., 2024 ) to web and app navigation ( Zhou et al., 2024 ; Zhang et al., 2025 ) .
An agent runs an iterative loop: it generates an action ( Yao et al., 2023 ) , executes it in a sandbox ( E2B, 2026 ) , observes the outcome, and refines its next step.
To push capability further, agents increasingly scale test-time compute ( Snell
et al., 2025 ) through tree search such as Monte Carlo Tree Search (MCTS) ( Zhou et al., 2024 ) and Tree of Thoughts ( Yao et al., 2023 ) , exploring multiple candidate paths, checking them against execution feedback, and backtracking from failures.

 In early text-based tasks (e.g., HotPotQA), backtracking cost almost nothing: the agent simply truncated its prompt history.
A coding agent, by contrast, acts on real OS state ( The OpenClaw
Project, 2026 ) through commands like rm , pip install , and sed .
These side effects persist on disk and cannot be undone by editing history. Reverting them requires checkpointing and restoring the complete sandbox state.
Because tree search backtracks constantly, this expensive rollback repeatedly hits the critical path—an infrastructure bottleneck.

 The sandbox state encompasses two tightly coupled dimensions: durable filesystem state and ephemeral process state.
These dimensions must be captured and restored jointly to prevent state divergence or context loss.

 Test-time search stresses checkpoint/restore (C/R) along two axes at once: horizontally, Best-of-N sampling spreads the inference budget across many parallel trajectories, each needing a fast initial clone ( Brown et al., 2024 ; Snell
et al., 2025 ) ; vertically, tree search such as MCTS backtracks to arbitrary historical nodes, demanding fine-grained C/R of intermediate states.

 Beyond test-time inference, RL training of agent policies is a second pressure point ( He
et al., 2026 ; Shao et al., 2024 ; Yu et al., 2025 ) .
Each training step must spin up N N independent sandboxes from the same warm starting state, run them as rollouts, and tear them down.
Today’s systems rebuild this warm state per rollout with a fresh Docker container or a microVM snapshot-restore, both in the hundreds-of-milliseconds to seconds regime. With N N in the tens to low hundreds, fork latency bounds training throughput.

 Existing systems manage filesystem and process state separately, achieving C/R by duplicating the entire state into a checkpoint image ( Daytona, 2024 ; Yan, 2025 ; The CRIU
Project, 2011 ; E2B, 2026 ; Agache et al., 2020 ) .
Full duplication is acceptable for serverless cold starts ( Ao
et al., 2022 ; Du
et al., 2020 ; Ustiugov et al., 2021 ; Chai et al., 2025 ) , but prohibitively slow for agents that checkpoint and roll back frequently on the critical path.
This creates three obstacles for agent workloads:

 Challenge-1: Existing durable filesystem C/R is coarse-grained and disruptive . 
A significant challenge is how to efficiently checkpoint and restore the durable filesystem state of an agent sandbox, including repository edits, installed packages, caches, and temporary files.
Naive file-level copying (e.g., copytree ) scales with the directory size, Docker commits scale with the mutated layer, and VM/block snapshots ( Agache et al., 2020 ) operate at a coarse whole-VM granularity.
These approaches are tolerable for occasional resets, but too slow for per-step rollback in MCTS or large fan-out in RL.
Overlayfs appears to be a natural alternative because each checkpoint could demote the current writable upper into a read-only lower and install a fresh upper, turning later writes into copy-on-write (CoW).
However, stock Linux overlayfs freezes its layer stack at mount time: changing the stack requires umount / mount , which is impossible while an agent keeps files or working directories open and also flushes dentry/inode caches ( Brown, 2026 ) .
Moreover, ordinary overlayfs copy-up can duplicate an entire inherited file for a small edit, causing file-size-proportional write amplification.

 Challenge-2: Whole-state dump and materialization limit process C/R efficiency. 
An agent’s process state is not just heap bytes: it includes the Python interpreter, loaded indexes, tool context, open descriptors, and SDK helper threads that make a sandbox warm.
Existing process C/R exposes a whole-state dump/materialize interface: checkpoint serializes the warm footprint, and restore reconstructs it, even when the agent changed little since the previous step.
This model is acceptable for serverless cold-start systems that optimize restore and treat snapshot creation as offline work ( Cvetković et al., 2024 ; Chai et al., 2025 ; Du
et al., 2020 ; Du
et al., 2022 ; Li et al., 2022 ; Yu et al., 2024 ; Huang et al., 2026 ; Szekely
et al., 2024 ) , but mismatched with agents, which checkpoint after nearly every action and restore on every backtrack or fork-out.
Whole-VM snapshots pause and copy unrelated guest state (E2B reports ∼ 4 {\sim}4  s per GiB ( E2B, 2026 ) ), while process-level CRIU ( The CRIU
Project, 2011 ) avoids VM scope but still serializes and reloads process pages, file mappings, and descriptors.

 Challenge-3: Coupled sandbox state requires explicit consistency management. 
Even if filesystem and process C/R are optimized in isolation, agents cannot restore the two dimensions independently.
Process memory contains open descriptors, mmap’d files, Python import caches, tool outputs, and assumptions about packages or tests on disk; the filesystem records the edits and side effects that this memory will continue to use after rollback.
A naive composition of overlayfs and CRIU can capture the two dimensions at different logical times, register a partially completed checkpoint after a failure, or resume a process before its target filesystem is installed.
Agent sandboxes therefore need explicit consistency management for an atomic, failure-aware (filesystem, process) state pair, not two unrelated snapshots.

 This paper observes that consecutive checkpoints in agent workloads differ only marginally, with only a few new files or modified memory pages between steps.
Therefore, instead of duplicating the entire state, a sandbox should only duplicate the changes between consecutive checkpoints ( Key Insight ).

 To this end, we present DeltaBox, an OS-level rollbackable sandbox tailored for stateful agents.
DeltaBox achieves millisecond-level checkpoint/rollback
through a new OS abstraction, DeltaState,
which treats the filesystem and process memory as a transactional, change-based state pair.
We introduce two co-designed OS mechanisms in DeltaBox, coordinated by a StateManager:

 Figure 1 . Per-event checkpoint/restore cost of existing approaches on SWE-Search , decomposed into filesystem, process/VM, and other phases (restore on a log axis). 

 Firstly, to support efficient filesystem C/R, we propose DeltaFS .
DeltaFS extends overlayfs with runtime layer switching , which reconfigures the layer stack without unmounting or closing open file descriptors.
This makes a checkpoint a metadata-only layer insertion that preserves history, while restore selects a recorded layer-stack configuration in O ⁡ ( 1 ) O(1) time. Reference-counted generations keep cached dentries and inodes safe while old stacks drain.
To keep the switch transparent to a live agent, DeltaFS adds a lazy switch for open files : per-inode version tags detect open files or mmap’d regions resolved before the checkpoint and re-resolve/copy them up on the next write.
Finally, DeltaFS uses XFS reflink under overlayfs copy-up, so unchanged extents remain shared across renamed generations and file updates pay only block-level CoW rather than file-size-proportional duplication.

 Secondly, to C/R process memory state efficiently, we design DeltaCR .
DeltaCR builds process checkpoints around a warm-template fast path: between actions, the agent inline-forks a frozen template while DeltaCR asynchronously dumps that template with CRIU, giving each checkpoint both a low-millisecond restore target and a durable fallback, with the work hidden inside the LLM I/O window.
On a template hit, fork-based restore spawns the restored agent by copying page tables rather than memory pages; on a miss, CRIU lazy-pages restore reconstructs the process on demand and reinserts it into the pool.
The template serves the common single-threaded agent at fork speed, while the CRIU image captures the whole process tree, extending the same protocol to multithreaded and multi-process agents.
To keep deep search bounded, DeltaCR skips read-only nodes to avoid snapshots for cheap-to-recompute actions, and reachability-aware garbage collection reclaims only snapshots the search can no longer select.
Finally, we propose async-warm to absorb post-fork CoW faults off the critical path. A network proxy daemon keeps LLM sockets and SDK threads outside the template so fork is safe. For RL fan-out, DeltaBox implements batched fork_n on top of the same template protocol.

 Thirdly, to keep memory and file views consistent, DeltaBox adds a StateManager and a coupled C/R protocol.
The StateManager maintains a snapshot index tree mirroring the search tree, where each node records the target overlay layer-stack configuration, CRIU dump path, and live template when available.
On checkpoint, the boundary between actions lets DeltaCR capture the post-action process and DeltaFS freeze the matching filesystem generation before the node becomes visible; on restore, DeltaBox switches the filesystem first and resumes the restored process only afterward.
This ordering keeps memory and file views mutually consistent, and serves rollback, evaluation-time test isolation, and batched RL fork-out.

 We implement DeltaFS as an overlayfs kernel module and DeltaCR as a userspace framework, integrating both in DeltaBox, an agent sandbox based on a Firecracker microVM.
End-to-end evaluations show that a checkpoint’s 10.83 ms of work is hidden under inference (zero agent-perceived blocking), while template-fork restore completes in a mean 1.86 ms. The CRIU lazy-pages fallback after template eviction restores in 9.29 ms.
On SWE-bench MCTS workloads, DeltaBox reduces state-management overhead from 39–51% of total time on the baselines to 1–2%.
For RL training fan-out, DeltaBox’s batched fork_n forks up to 64 rollouts from one warm template at 0.55–5.1 ms per child.
End-to-end fan-out is 10.4 × 10.4\times – 24.7 × 24.7\times faster than CubeSandbox and E2B.

 2.1. Search and Exploration for AI Agents

 Modern LLM-based agents increasingly rely on search and exploration, whether tree-structured or parallel sampling, to solve complex tasks such as math and code ( Jimenez et al., 2024 ) .

 MCTS. 
MCTS is a tree-search algorithm that cycles through selection, expansion, evaluation, and backpropagation ( Kocsis and
Szepesvári, 2006 ; Browne
et al., 2012 ) . LATS ( Zhou et al., 2024 ) adapts it to LLM agents, using UCT-guided selection to pick the most promising node and then generating and executing candidate actions in a sandbox.
SWE-Search ( Antoniades et al., 2025 ) specializes this loop to SWE-bench code repair, improving the success rate over single linear generation.

 Best-of-N. 
BoN runs N N independent trajectories from the same initial state and keeps the best by execution feedback ( Brown et al., 2024 ; Snell
et al., 2025 ) , i.e., N N clones of the initial environment.

 RL training. 
RL post-training fans out rollouts (i.e., inference and agent exploration) at every training step. Chain-based algorithms such as GRPO ( Shao et al., 2024 ) launch N N independent rollouts from the same initial state and score the completed trajectories. Tree-based variants such as Tree-GRPO ( Ji
et al., 2026 ) instead branch additional rollouts from intermediate states of existing trajectories, sharing the common prefix instead of re-executing it. Either way the fan-out recurs at every training step, so sandbox cloning latency directly gates training throughput. Tree-based RL additionally requires forking from arbitrary mid-trajectory states.

 2.2. Agent Sandbox and Coupled Checkpoint/Restore

 Sandbox runtimes ( Agache et al., 2020 ; Du
et al., 2020 ) typically provide two critical primitives for agent exploration— checkpoint and rollback —letting agents execute code in isolation, capture milestone snapshots, and safely revert after failures.
RL fan-out ( §​ 2.1 ) uses the same mechanism: the runtime checkpoints one warm environment and restores it N N times, once per rollout.

 While most modern agent frameworks utilize some form of checkpoint and rollback, their implementations are often inefficient or incomplete.
For example, SWE-agent ( Yang et al., 2024 ) and OpenHands ( Wang et al., 2025 ) run the agent control logic on the host and reset the in-sandbox repository using Git.
However, this approach fails to checkpoint the running process,
leading to a loss of the execution context (e.g., debugging history).
To preserve this context, current frameworks interact with the environment via a persistent daemon process inside the sandbox (e.g., E2B’s envd ( E2B, 2026 ) ).
In this setup, a rollback only undoes file edits, leaving the process state desynchronized.
Recovering the true process state requires replaying every prior action from the initial state, which is a latency-heavy operation proportional to the search depth and may severely bottleneck the critical path of backtracking search.

 Coupled C/R matters. 
The state of a sandbox spans two interdependent dimensions:
the filesystem (FS) (working directories, installed packages)
and the process memory (execution context, open file descriptors).
A partial rollback inevitably desynchronizes them.
If only the FS is rolled back, the still-live process retains memory of file contents that no longer exist on disk.
Conversely, if only the process is rolled back, its restored memory operates on files that have been mutated beyond its expected state.
Either mismatch breaks the strict consistency required for correct tree search ( §​ 6.3.3 ), necessitating a truly coupled C/R mechanism.

 2.3. Why Existing Approaches Fall Short

 We summarize existing agent sandboxes in Table 1 .

 Checkpoint latency matters in agents. 
Although sandboxing is well studied in contexts like serverless computing, existing optimizations predominantly focus on minimizing restore latency to mitigate cold starts ( Du
et al., 2020 ; Agache et al., 2020 ; Huang et al., 2026 ; Oakes et al., 2018 ) .
However, in agents, the checkpoint operation also sits squarely on the critical path: an agent cannot proceed until its state is safely snapshotted .
This creates a new performance requirement that prior systems overlook.

 Efficient coupled C/R is difficult. 
Furthermore, existing systems manage filesystem and process states in isolation, failing to provide the coupled C/R efficiency required by agents, as shown in Table 1 .
 Filesystem-only methods (e.g., Git worktree ( Anthropic, [n. d.] ) ) version files but discard process memory, forcing expensive agent restarts.
Conversely, Process/VM-only methods (e.g., Firecracker snapshots ( Agache et al., 2020 ) , CRIU) capture memory but fail to coordinate with the underlying block device, necessitating separate, uncoupled filesystem snapshots.

 A quantitative analysis. 
 Fig. 1 breaks down the per-event C/R latency we measured for self-hosted E2B ( E2B, 2026 ) (incremental snapshots), CubeSandbox ( Tencent Cloud, 2026 ) , and a copytree+replay baseline.
Both VM-based sandboxes spend little time on the filesystem (at most 11% of any operation), with most time spent on VM state management and guest readiness.
CubeSandbox spends 84% of its 839.8 ms checkpoint creating the VM memory snapshot, and E2B’s 1072.0 ms checkpoint pauses the VM, snapshots it, and resumes it before the agent can respond again.
On restore, waiting for the agent’s first response after the VM resumes takes 61% of E2B’s 424.7 ms (85% including envd re-initialization) and 54% of CubeSandbox’s 643.9 ms.
The copytree+replay baseline keeps no process checkpoint: copying files takes only 4% of its 14.2 s restore, while restarting the agent and reloading its indexes (45%) and re-executing prior actions (51%) take the rest.
These costs make repeated state transitions expensive, even though each MCTS step changes only a small fraction of sandbox state ( Fig. 2 ).

 2.4. Insight: Delta-Based Checkpoint and Restore

 We analyzed state changes in SWE-Search MCTS trajectories ( Fig. 2 ).
Per step, process memory and filesystem deltas average only 12.2% and ∼ 0.005 % {\sim}0.005\% of their total state, respectively ( Fig. 2 (a)), consistently across rounds and workloads.
Small state deltas persist across MCTS steps ( Fig. 2 (b)).

 This observation leads to our core idea:
rather than duplicating the entire sandbox state, an efficient agent sandbox should only capture and restore the state deltas between consecutive checkpoints ( Key Insight ), bypassing the I/O and memory-copy overheads of full-system C/R.

 3. Overview

 Based on the insight, we present DeltaBox, a new agent sandbox realizing millisecond-scale C/R.

 3.1. System Architecture

 DeltaBox extends existing sandboxes (e.g., microVMs) with two key components: DeltaFS and DeltaCR.

 DeltaFS: Delta-based filesystem. 
A fundamental challenge for DeltaBox is efficient C/R of filesystem state.
A natural approach is to apply CoW to the filesystem: keep existing files read-only and copy them only when modified, so each checkpoint need only record changes since the previous checkpoint.

 Overlayfs ( Brown, 2026 ) offers the closest realization of this idea.
It provisions a writable upper layer for apps while maintaining a read-only lower layer that encapsulates the base sandbox image.
However, overlayfs suffers from a critical limitation:
its layer stack is fixed and static at mount time.

 To resolve this, we introduce DeltaFS, a new filesystem extending overlayfs that supports dynamic, runtime overlay reconfiguration.
When an agent completes a task step and requests a checkpoint, DeltaFS does not duplicate the underlying files.
Instead, it dynamically freezes the current writable layer into a read-only state and seamlessly inserts a new writable upper layer on top of it.
Consequently, all subsequent file updates trigger CoW to this new upper layer.
Through this mechanism, a checkpoint operation is reduced to a lightweight layer-insertion, and a rollback becomes a simple layer-removal, aligning with our diff-based C/R insight.
DeltaFS further uses reflink-enabled XFS, whose block-level CoW keeps copy-up cost proportional to the blocks actually written ( §​ 4.1 ).

 DeltaCR: Delta-based process checkpoint/restore. 
Process-level state management has seen extensive prior research.
Methods like CRIU ( The CRIU
Project, 2011 ) and fork() ( Du
et al., 2020 ; Wei
et al., 2023 ) are widely used.
However, applying them directly to agent workloads presents severe challenges.
While recent efforts have optimized CRIU’s restore latency, its checkpoint latency, even using incremental dumps ( The CRIU
Project, 2016 ) ,
remains 100–1,000 ms.
While fork() offers millisecond-scale cloning,
it introduces its own limitations:
(1) it requires the parent process (template) to remain resident in memory, scaling poorly for agent exploration;
(2) CoW page faults add latency right after each restore;
and (3) both CRIU and fork() are only safe if the process holds no long-lived external state.
Standard Python LLM SDKs (e.g., OpenAI) violate this by holding long-lived connections.

 To this end,
DeltaBox introduces DeltaCR, a hybrid process C/R mechanism that synthesizes the durability of CRIU with the speed of fork() .
During a checkpoint, DeltaCR simultaneously executes an asynchronous CRIU incremental dump and a template-creating fork() ,
hiding both operations within the LLM I/O window.
During a restore, DeltaBox prioritizes the fast-path by forking the resident template.
To bound memory costs, DeltaCR employs a template pool, transparently falling back to CRIU’s lazy-pages restore if the template has been evicted.
DeltaCR includes an optional async-warm thread that absorbs post-fork CoW faults off the critical path ( §​ 4.2.2 ), alongside a network proxy daemon that keeps persistent I/O connections outside the agent process so the frozen template remains forkable.

 Coordination and optimizations. 
To ensure atomic, coupled state transitions,
DeltaBox employs a two-tiered StateManager to orchestrate DeltaFS and DeltaCR, maintaining each checkpoint as one DeltaState: a consistent, transactional (filesystem, memory) pair.
The global Sandbox Controller runs on the host, maintaining a snapshot index tree isomorphic to the search tree,
where each node records its CRIU dump path and overlay layer-stack configuration.
Simultaneously, the Guest Daemon executes the local C/R sequences inside the VM,
keeping state management off the host’s critical path ( §​ 5 ).

 DeltaBox also introduces agent-specific optimizations to further minimize overhead.
First, a semantic-aware lightweight skip mechanism avoids unnecessary snapshots.
Second, DeltaBox utilizes a reachability-aware garbage collector ,
to reclaim unused checkpoints.

 3.2. System Workflow

 Fig. 3 shows the overall workflow of DeltaBox.
DeltaBox efficiently supports two critical workloads: millisecond-scale rollback to a prior node for tree search, and rapid N N -way fork-out from a frozen template for parallel RL training.

 3.2.1. Coupled deltaCheckpoint and deltaRestore

 We introduce the workflow of two primitives.

 deltaCheckpoint. 
A checkpoint operation is orchestrated by the StateManager and executed entirely off the host’s critical path by the Guest Daemon inside the sandbox.
First, the daemon captures the process state via DeltaCR: the agent executes a fork() at a quiescent point to create a frozen template, while a CRIU incremental dump is asynchronously submitted.
Concurrently, the daemon triggers the DeltaFS ioctl to freeze the current FS upper layer and install a fresh writable layer.
The agent remains perfectly quiescent across both operations.
This guarantees that every deltaCheckpoint registers a strictly consistent (FS, memory) state delta.
Because this entire sequence executes concurrently while the agent awaits its LLM response, the checkpoint cost is hidden behind inference latency.

 deltaRestore. 
A restore operation seamlessly reverses this process.
On rollback, the Sandbox Controller instructs the Guest Daemon to discard the current active agent.
The daemon then uses the DeltaFS ioctl to dynamically revert the FS layer stack to the target checkpoint’s exact configuration.
Simultaneously, DeltaCR rebuilds the process memory.
If the target’s frozen template is still resident in the pool, DeltaCR executes a millisecond fork() (the fast path); otherwise, it falls back to a CRIU lazy-pages restore.
The new agent process then resumes execution from the exact instruction immediately following the original checkpoint, entirely unaware of the rollback, with its FS and memory perfectly synchronized.

 3.2.2. Fork-out

 Fork-out composes the same two primitives differently: rather than restoring one past state, it instantiates N N children from one checkpoint, chain-based RL from the warm initial state and tree-based RL from any mid-trajectory checkpoint ( §​ 2.1 ).
The StateManager takes a deltaCheckpoint at the source state, then forks the checkpoint’s frozen template N N times in one batched fork_n request, each child receiving a private filesystem view over the frozen layers ( §​ 4.2.1 ).
Each child starts with its memory CoW-shared with its siblings, at the same millisecond-scale per-child cost as a fast-path deltaRestore ( §​ 6.2.2 ).

 3.3. Branch-Level Containment Model

 A branch is one search path or forked rollout of a task, and DeltaBox isolates branches within a single VM at process and file granularity: each branch runs in a separate process with a private writable overlay upper, while frozen ancestor layers and read-only base layers are shared.
The guest kernel, network proxy, and files outside the DeltaFS-managed task repository are shared and not checkpointed.
Rolling back one branch thus leaves its siblings untouched.
Existing agent sandboxes (e.g., E2B ( E2B, 2026 ) and CubeSandbox ( Tencent Cloud, 2026 ) ) usually snapshot and clone whole VMs, so each branch typically runs in its own VM, whereas DeltaBox isolates many branches inside one.

 External effects. 
DeltaBox rolls back only state inside the sandbox: the network proxy keeps communication continuous across checkpoints and restores ( §​ 4.2.3 ) but undoes nothing remotely.
Stateless LLM requests and idempotent operations (e.g., package downloads) ( Ding
et al., 2023 ) are simply reissued after a restore, whereas stateful remote operations (e.g., database writes) need cooperation beyond the sandbox ( Elnozahy
et al., 2002 ) , such as service-side transactions, deferred outputs, or compensating actions.

 4. Detailed Design

 4.1. DeltaFS: Dynamic Overlay Filesystem

 Figure 4 . DeltaFS architecture. (a) Standard overlayfs has a static layer stack. (b) DeltaFS reconfigures it at runtime: a checkpoint inserts a fresh writable upper, and a rollback switches to the target configuration; checkpoint_gen stamps each switch with a new generation. 

 Overlayfs fixes its layer stack at mount time. With live file references, remounting either fails or leaves the agent on a stale stack, and releasing those references means restarting the agent worker (0.4–17 s in our workloads).
As shown in Fig. 4 , DeltaFS lifts
this restriction and supports dynamic layers, switching the stack in 0.19 ms ( Table 3 ) while the agent keeps its process and descriptor state.

 Interface. 
To expose this dynamic capability, DeltaFS introduces a hotswitch ioctl that reconfigures the overlay layer stack in place to a target state: a writable upper layer above an ordered chain of read-only lower layers.

 During a checkpoint, if the current upper is dirty, the StateManager uses this interface to sink it into a frozen lower layer and install a new writable upper layer above it.
Consequently, files in the prior layer remain reachable, but any subsequent modifications trigger CoW to the new upper layer,
isolating the state delta.
The restore path is even simpler: the StateManager invokes the ioctl to specify the exact lower layer chain of the target checkpoint and installs a fresh writable upper layer above it.
Because this process is purely a layer reconfiguration, it takes O ⁡ ( 1 ) O(1) time regardless of how far back in the search tree the target checkpoint lies.
Path lookups still walk the active stack, so their latency grows with its depth ( Fig. 9 (c)). Since only dirty checkpoints add a layer, the stack stays within the search-tree depth ( ≤ 15 {\leq}15 in our workloads).
The ioctl is entirely synchronous; once it returns, subsequent path resolution observes the new stack; already-open descriptors are handled by the lazy rebinding mechanism below.

 Layer lifetime. 
A hot-switch completes without freezing the filesystem, so open files and in-flight lookups may still reference the old layer stack after the ioctl returns.
DeltaFS therefore reference-counts each retired stack: a cached overlay entry holds a reference to the stack it was resolved against, and the kernel frees a retired stack only after its last reference drops and an RCU grace period has elapsed.

 Open files across checkpoint and restore. 

Files opened prior to a checkpoint present a challenge: their FDs may point to backing files within an outdated layer stack.
DeltaFS resolves this via a generation-based lazy rebinding mechanism.
Each inode caches the checkpoint_gen at which it was last resolved.
During any file access, the kernel compares this cached generation against the current global filesystem generation.
If the generations match, the access proceeds directly via the fast path with near-zero overhead.
If they differ, the kernel re-resolves the inode against the new layer stack: read-side accesses only refresh stale references and keep reading from read-only layers, while write-side accesses first detach the descriptor from its stale backing and redirect it to the current writable upper, copying file data when needed.
Both paths update the inode’s generation and backing under a per-inode mutex.
Furthermore, if concurrent threads race to copy up the same file, the loser simply reuses the already-created upper layer rather than retaining its stale backing file.

 Descriptor semantics. 
A rollback replaces the filesystem view underneath live file descriptors.
DeltaFS makes this deterministic. After a
checkpoint, writing through a stale descriptor copies up from its frozen
backing into the current upper, so checkpointed history remains immutable.
After a restore, a descriptor whose path exists in the target state rebinds
reads and later copy-ups to that state.
If the file existed only in a discarded
upper,
the descriptor continues through an anonymous backing copy and never
resurrects the old path.

 XFS reflink. 

Layer switching and lazy rebinding work over any backing FS that overlayfs
supports. Reflink only bounds copy-up cost. DeltaBox uses reflink-enabled XFS, on
which stock overlayfs copy-up clones extents by reference: an edit duplicates
only the 4 KB blocks it overwrites, and unmodified extents stay shared across
generations. On other FSes (e.g., ext4), copy-up duplicates whole files
( §​ 6.3.2 ).

 4.2. DeltaCR: Diff-based Checkpoint/Restore

 DeltaCR manages the process (memory) dimension of each checkpoint around two paths: a warm-template fast path, which checkpoints by forking off a frozen template and restores by forking it back in low milliseconds, and a durable CRIU ( The CRIU
Project, 2011 ) fallback, with incremental dumps via soft-dirty page tracking and lazy-pages restores via userfaultfd ( The CRIU
Project, 2019 ) ( Fig. 5 ).

 Figure 5 . DeltaCR architecture. Checkpointing creates both a CRIU image and a frozen template. Restores use the template fast path on hit, or the CRIU image on miss; the network proxy (NPD) keeps external I/O off the agent path. \agentcrcontroller checkpoints an active agent into a CRIU image and a frozen template pool. Restore uses the template pool on hit, the CRIU image on miss, and a sidecar for LLM network proxying. 

 4.2.1. Template Pool and Fork-Based Restore

 The fast-path restore mechanism relies on a template pool , which maintains a registry of frozen (SIGSTOP’d) processes, each keyed to a specific snapshot ID.

 Inference-masked checkpointing. 
A checkpoint runs while the agent awaits its LLM response, so both its fork and its dump are hidden inside the inference window.
Checkpoint k k starts once the agent finishes an action and is quiescent (no syscalls in flight, no files half-written): the agent forks, and the frozen child registers as template_k in the pool while the active worker continues in the main loop.
DeltaCR then takes an incremental dump in the background as a durable fallback for crash recovery and cold-path restores.
Meanwhile, the agent’s LLM connection lives in the network proxy ( §​ 4.2.3 ), so the request keeps progressing.

 Fast-path restore (template hit). 
To restore checkpoint k k while template_k is alive, the Guest Daemon
kills the current agent, reverts the layer stack, and forks template_k .
The child resumes via SIGCONT from the instruction right after the original
checkpoint, with the filesystem already switched to match.
The fork duplicates only page tables, so restore completes in low milliseconds.
An optional async-warm thread absorbs the
post-fork CoW faults off the critical path.
The C/R protocol makes the worker single-threaded at the moment it forks:
the fork happens only at a quiescent point, after transient thread pools are
shut down, and long-lived network threads live in the separate proxy process
( §​ 4.2.3 ).
If threads or child processes remain alive at a checkpoint, DeltaBox forgoes the
template and restores from the CRIU image, which captures the whole process tree,
including its threads, descriptors, and internal pipes.

 Slow-path restore (template miss). 
If template_k has been evicted, DeltaCR falls back to CRIU lazy-pages restore.
CRIU reconstructs the process skeleton, registers all anonymous VMAs with userfaultfd, and resumes the process, faulting in pages on demand from the dump images.

 N N -way fork-out ( fork_n ). 

RL fan-out ( §​ 3.2.2 ) reuses the template-fork protocol through a batching primitive that we implement in DeltaBox: fork_n wakes the frozen template once, forks all N N children in one cycle, and re-suspends it, eliminating N − 1 N{-}1 per-child resume/suspend round-trips compared with issuing N N one-at-a-time template restores.
FS isolation is per child: the source’s overlay layers are frozen once at the branch point (one DeltaFS ioctl),
and each child receives its own overlay mount whose read-only lowers are the frozen chain and whose writable upper is private, so isolating a child costs one mount and no data copy.
These mounts are pre-created before the fork, so every child resumes directly into a ready, private filesystem view.

 4.2.2. Bounding Memory under Deep Search

 By default DeltaCR writes each CRIU dump to an image file on the FS, kept in the page cache for fast cold-path restore but reclaimable under memory pressure. A checkpoint’s unreclaimable resident cost is therefore just its frozen template (CoW page tables and privatized pages).
Unlike fan-out, whose children share one template’s pages, deep search keeps a template per historical checkpoint, each pinning the pages its branch has since modified.
Left unbounded, resident memory grows 4.7 × \times within 28 checkpoints ( Fig. 6 a) and keeps growing until the guest exhausts memory.
DeltaBox bounds it along three complementary axes: it avoids creating snapshots for cheap-to-recompute nodes, caps the resident template set, and reclaims snapshots the search can no longer reach.

 Skipping read-only nodes. 
Many agent actions, such as grep , cat , and find , are read-only and idempotent: they leave the filesystem untouched, so re-executing one reproduces its effect on the agent.
Our rule-based classifier marks an action read-only only if every command in it, including each pipeline stage, is on a read-only allowlist (e.g., cat , grep , sed without -i ) and nothing is redirected to a file. Any other or unparsable action gets a standard checkpoint.
For a read-only node, DeltaBox skips the template fork and CRIU dump, recording only a metadata marker (parent snapshot ID and action). The layer switch still runs whenever the upper layer is dirty, so a misclassified write is not lost.
A restore to that node restores its nearest fully checkpointed ancestor and re-issues the read-only actions skipped since then, reproducing the node’s state.
Because read-only steps dominate a typical trajectory (77% of checkpoints in Fig. 6 b), this avoids creating most snapshots and sharply lowers the snapshot-store footprint, at the cost of a replay on restore.
DeltaBox therefore enables it only when snapshot memory, rather than restore latency, is the bottleneck.

 Bounded template pool. 
When resident template memory becomes the bottleneck, the pool caps the live set at N tpl N_{\text{tpl}} frozen templates under LRU eviction.
Evicting a template increases restore latency but preserves correctness.
Its CRIU image remains on the snapshot store, so a later re-selection falls back to the slow path ( §​ 4.2.1 ).

 Reachability-aware garbage collection. 

A recency- or visit-count policy is unsafe for MCTS: discarding a node UCT may still select, or an ancestor whose delta image a reachable node’s incremental dump chains back to, triggers a restore-fail re-selection loop that wastes the iteration budget.
DeltaBox instead drives GC from a persistent node-to-image index , in which each node records its parent, children, and delta-image ID.
A pass marks the reachable set and reclaims the rest at leaf or whole-subtree granularity.
A delta image is freed only when its node is unreachable and no reachable descendant or shared node depends on it, so reclamation never breaks the --prev-images-dir chain.
Since an unreachable node is never re-selected, GC drops both its frozen template and, when on-disk image storage is scarce, its delta image. GC runs asynchronously, off the checkpoint critical path.
 Fig. 6 a shows the combined effect: with no policy, resident memory climbs with tree depth; lightweight-skip and reachability-GC keep it flat. Lightweight-skip additionally diverts most read-only nodes to a near-free metadata write ( Fig. 6 b).

 Figure 6 . Bounding memory under deep search. (a) Resident memory (template pool and active worker) vs. MCTS iteration under four retention policies. (b) Per-event checkpoint latency with and without lightweight-skip. 

 Async-warm. 

After a fork, the child shares all pages with the template using CoW, so its first write to each page takes a synchronous CoW fault.
An async-warm thread in the Guest Daemon (keeping the agent single-threaded) absorbs these faults off the critical path: right after the fork it walks the child’s anonymous writable VMAs via /proc/[pid]/mem , forcing each page’s private copy in the background while the child runs.
The latency win is not free: privatizing every page destroys CoW sharing with the template (over 5 × 5\times resident inflation, Fig. 6 a) and marks every touched page soft-dirty, degrading the next incremental dump to a full one.
Since post-restore CoW faults are small next to LLM and tool latency, DeltaBox disables async-warm by default, enabling it only when they, rather than memory, are the bottleneck.

 4.2.3. Reusable I/O during Checkpoint with a Network Proxy

 Fork-based restore is safe only if the frozen template’s address space holds no long-lived external state, such as live network threads. However, Python LLM clients keep connection pools and background threads in the agent process.
Forking such a template leaves half-open sockets and locks held by threads that fork does not copy, causing runtime failures.

 DeltaBox resolves this with a network proxy daemon , a separate process in the same sandbox that owns all LLM clients and connections.
The agent never links the SDKs. It exchanges small FIFO tokens (each ≤ \leq   PIPE_BUF , hence atomic) with the proxy over a shared directory, keeping every socket and SDK thread out of its address space.
Being a separate process, the proxy is excluded from both the CRIU dump and the template fork, so a template carries only the agent’s own short-lived threads.
During a checkpoint the agent pauses only to inline-fork. The in-flight LLM request keeps progressing inside the proxy, which buffers the response until the agent resumes.
After a fork-based restore the child inherits the FIFO descriptors from the template, resuming communication with no reconnection protocol.
Network side effects are discussed in §​ 3.3 .

 4.3. StateManager Coupling Protocol

 StateManager coordinates the system to enforce an invariant: every saved state is a consistent (filesystem, memory) pair .

 Consistency protocol. 
During a checkpoint, consistency rests on a quiescence invariant :
the worker replies only after finishing its action and returning to a single-threaded control point, where it blocks on its control FIFO until the next command.
The fork (memory) and the DeltaFS ioctl (filesystem) therefore observe the same post-action state, and the asynchronous dump serializes the corresponding quiescent process state.
During a restore, the restored child blocks at the same control point, and the StateManager issues it commands only after both the layer switch and the fork have completed, so the agent never executes against mismatched files.

 Failure atomicity and concurrency. 
DeltaBox is failure-atomic at the level of checkpoint visibility:
a checkpoint becomes restore-visible only at its final registration step, so a crash mid-sequence leaves the partial checkpoint unreferenced, and registered checkpoints keep their frozen layers, which are immutable.
A slow-path restore that needs the CRIU image waits for any in-flight dump to complete; the fast path reads only the frozen template.
On restore, the template fork proceeds concurrently with the layer switch (the two touch disjoint kernel state); the synchronization point is the next-command boundary above, not the fork itself.

 Evaluation-time test isolation. 
Evaluating a node often runs tests (e.g., SWE-Search ( Antoniades et al., 2025 ) ),
whose side effects such as __pycache__ , pytest caches, and
temporary files would permanently pollute a stateful, in-process worker.
Stateless sandboxes avoid this only by discarding the sandbox, whereas DeltaBox instead uses its own millisecond C/R primitive as a transaction bracket:
the StateManager checkpoints before the test, restores once the result is
collected, and then records the result as the node’s observation and
reward. This is only practical because DeltaBox makes coupled C/R a
millisecond-scale primitive rather than a second-scale sandbox operation.

 5. Implementation and Deployment

 DeltaBox is deployed inside Firecracker ( Agache et al., 2020 ) microVMs. The design is not Firecracker-specific and carries over to container- or other VM-based sandboxes.
DeltaFS adds ∼ 1.8 {\sim}1.8 K LOC of C to overlayfs, all inside its loadable kernel module. It builds against stock Linux 6.8 and needs no VFS or other kernel changes.
DeltaCR is ∼ 3.8 {\sim}3.8 K LOC of Python orchestrating CRIU, the template pool, the async-warm thread, and the network proxy ( §​ 4.2 ).
The fork-out path ( §​ 4.2.1 ) is a separate ∼ 330 {\sim}330 -LOC module that adds the batched fork_n op to the template pool’s control-FIFO protocol.
CRIU dump images and overlay uppers both reside on the XFS rootfs, where reflink CoW is block-granular. Recent dump images stay in the page cache for fast restore and are reclaimed under memory pressure.

 Deployment model. 

The StateManager’s two tiers ( §​ 3 ) map onto a Host–Guest split: the host-side Sandbox Controller manages VM lifecycle and workload provisioning, while the in-VM Guest Daemon owns the entire per-event C/R sequence, keeping all latency-sensitive work in a closed loop inside the guest; the KVM host is unmodified.
Branches of a task share its VM under the containment model of §​ 3.3 .

 Integrations. 
We integrated DeltaBox with several agent systems via out-of-tree adapters tailored to where each keeps its state.
 Sandbox-resident execution workers (e.g., SWE-agent ( Yang et al., 2024 ) ): at action boundaries, coupled C/R ( §​ 4.3 ) checkpoints the worker and binds each search node to its checkpoint ( ∼ 500 {\sim}500 LOC).
 Host-side orchestration (e.g., LangGraph ( LangChain, Inc., 2024 ) ): LangGraph provides no sandbox, so the integrator defines the execution boundary; the framework keeps logical state on the host, while DeltaBox keeps the sandbox’s filesystem and process state ( ∼ 800 {\sim}800 LOC).
 Multithreaded agent loops that spawn tool processes (e.g., Codex): a wrapper launches the agent under a managed process-tree root and invokes coupled C/R at action boundaries, where CRIU captures the agent’s threads and live tool subprocesses; Codex’s exec-server interface can also forward tool execution into DeltaBox ( ∼ 2.2 {\sim}2.2 K LOC).
Porting DeltaBox to Kata Containers took ∼ 600 {\sim}600 LOC for sidecar-worker C/R integration.

 6.3. Extended Studies

 6.3.1. Checkpoint/Restore Latency

 We present the detailed latency breakdown in Table 3 , alongside the corresponding phases of CRIU+cp to separate the contributions of DeltaFS and DeltaCR.
DeltaFS replaces the file copy with a sub-millisecond layer switch, and DeltaCR replaces the synchronous dump and lazy-pages restore with an asynchronous dump and a millisecond-scale template fork.

 Checkpoint latency. 
Per-step checkpoint latency is dominated by the template-fork tail. The incremental CRIU dump runs asynchronously ( Table 3 ).

 Restore latency. 
On the fast path, the template fork dominates and the DeltaFS ioctl overlaps with it inside the fork window.
The slow path, taken only after template eviction, is dominated by CRIU restore ( Table 3 ).
The layer switch likewise overlaps CRIU on the slow path. In contrast, CRIU+cp must finish its file copy before CRIU reopens files by path, so its restore phases add up.
Both slow paths use CRIU lazy-pages restore.
DeltaBox keeps persistent LLM connections and SDK threads in a separate proxy daemon ( §​ 4.2.3 ), outside the process state reconstructed by CRIU.
CRIU restore latency increases with incremental-chain length ( Fig. 9 (d)).
DeltaBox implements asynchronous merging of incremental checkpoint chains to mitigate this overhead.

 6.3.2. Write Amplification

 We measure physical I/O (bytes written to the block device, including journal and metadata) across ext4, XFS, and XFS+reflink under two workloads: a fixed 4 KiB overwrite of 4 KiB–1 MiB files, which isolates the copy-up cost ( Fig. 9 (a)), and replayed real SWE-Search agent edits on 1–256 KiB files ( Fig. 9 (b)).

 Copy-up savings. 
 Fig. 9 (a) shows that ext4 and XFS without reflink both recopy the whole file on every edit, growing linearly with file size, whereas reflink copy-up stays flat because it duplicates only the dirtied blocks.

 Physical I/O. 
 Fig. 9 (b) shows that XFS’s lighter metadata dominates the I/O savings on small files (136 KiB → \rightarrow 27 KiB at 1–8 KiB), and reflink’s block sharing on large files (320.5 KiB → \rightarrow 174 KiB at 128–256 KiB).

 6.3.3. Correctness

 An integration suite of 61 checks drives the DeltaFS ioctl directly, covering checkpoint semantics across generations, file and directory operations after a switch, stale and deleted-but-open descriptors, mmap, and copy-up integrity; all pass.
Invalid requests are rejected atomically with the mount still writable, and layer chains stay valid up to overlayfs’s 500-layer cap.

 7. Related Work

 Agent sandboxes. 
Recent agent sandboxes ( Daytona, 2024 ; E2B, 2026 ; ZeroBoot, 2026 ; Yan, 2025 ) primarily optimize isolation and startup latency, but provide only coarse-grained rollback.
Daytona’s OCI workspaces ( Daytona, 2024 ) use Docker-layer commits and do not capture live process state.
E2B ( E2B, 2026 ) uses Firecracker microVMs and pre-warmed templates, improving isolation but retaining VM-granularity snapshot costs.
ZeroBoot ( ZeroBoot, 2026 ) pushes VM cloning further with KVM-level CoW memory, but it forks from a fixed template whose update needs a full ∼ 15 {\sim}15  s re-snapshot without incremental checkpoints, and each branch remains an entire VM, with a shared block device, kernel-level dirty state, and no independent rollback for multiple in-VM trajectories.
Yan’s fault-tolerant sandbox ( Yan, 2025 ) moves toward transactional agent execution, but its filesystem rollback based on tool interception and userspace CoW simulation yields second-scale checkpoints and no coupled memory snapshot.

 A position paper ( Xu
et al., 2025 ) frames agentic exploration as a systems problem and, like DeltaBox, identifies fast forking and fork-aware state management as foundational gaps; it remains a diagnostic framing, whereas DeltaBox contributes a concrete millisecond-scale OS mechanism.
BranchFS ( Wang and Zheng, 2026 ) likewise targets agentic exploration, offering fork/explore/commit branch contexts with first-commit-wins semantics. Its FUSE prototype isolates only filesystem state, whereas DeltaBox checkpoints and restores coupled filesystem and process state.

 Concurrent work Crab ( Wu
et al., 2026 ) tackles the same gap from a different angle.
Crab proposes a semantics-aware approach using an eBPF-based inspector to determine checkpoint granularities.
In contrast, DeltaBox focuses on optimizing the full OS-level C/R mechanism itself to achieve millisecond latency.
The two approaches are complementary.
DSec ( Huang
et al., 2026 ) , DeepSeek’s production platform for agentic training, hosts over 380K concurrent sandboxes. Like DeltaBox, it layers sandbox filesystems with overlayfs, but composes the layers only at creation and does not roll back running sandboxes; DeltaBox switches layers at runtime to restore coupled filesystem and process state.

 Sandboxes for serverless computing. 
Serverless systems have long optimized sandbox reuse, cold start, and snapshot restore, but their unit of reuse is a function invocation rather than a rollback point inside a long-lived agent trajectory.
TrEnv-X ( Huang et al., 2026 ) repurposes sandboxes across invocations using OS-level memory templates backed by CXL or RDMA memory pools, while earlier cold-start systems accelerate process creation, language runtime initialization, or post-restore fault handling for short-lived functions ( Du
et al., 2020 ; Cadden et al., 2020 ; Oakes et al., 2018 ; Ustiugov et al., 2021 ; Ao
et al., 2022 ; Holmes et al., 2025 ) ; Spice ( Holmes et al., 2025 ) moves restore-path fault resolution into the kernel with Overlay VMAs.
Dandelion ( Kuchler
et al., 2025 ) cold-starts syscall-free compute functions in hundreds of microseconds, but runs each function to completion and keeps no long-lived execution state to roll back.
They are orthogonal to DeltaBox. A serverless instance typically restores a compute image and then runs one request, whereas DeltaBox repeatedly descends and backtracks within one task.

 Checkpointing optimizations. 
Existing checkpointing systems ( Yang
et al., 2024 ; Tullmann
et al., 1996 ; Vogt et al., 2015 ; Dearle and Hulse, 1995 ; Tsalapatis et al., 2021 ; Plank
et al., 1995 ) provide important building blocks, but none provide the coupled, fine-grained rollback interface needed by stateful agents.
CRIU ( The CRIU
Project, 2011 ) (which DeltaCR builds on) and DMTCP ( Ansel
et al., 2009 ) do process-level C/R but not the coupled, high-frequency rollback agents require. Firecracker ( Agache et al., 2020 ) and Sabre ( Lazarev et al., 2024 ) restore whole VMs, too coarse for branches isolated inside one VM. Btrfs ( The Btrfs
Project, 2009 ) and ZFS ( OpenZFS, 2013 ) snapshots give block-level CoW but need a separate storage stack, and EROFS ( Linux Kernel
Project, 2018 ) offers read-only overlay layers without a writable upperdir; DeltaFS instead hot-switches overlayfs layers over XFS reflinks. LangGraph ( LangChain, Inc., 2024 ) and LangChain ( LangChain, Inc., 2022 ) checkpoint only logical agent state, which cannot undo executed commands’ OS-level effects.

 8. Conclusion

 We present DeltaBox, an OS-level rollbackable sandbox designed to accelerate agent workloads such as test-time tree search and RL.
Recognizing that subsequent agent states are highly similar, DeltaBox eschews full state duplication in favor of diff-based C/R. To achieve this, DeltaFS enables dynamic, unmount-free overlayfs layer switching for filesystem C/R, while DeltaCR utilizes CRIU dumps and warm-template forking for memory C/R.
The DeltaBox artifact is available at https://doi.org/10.5281/zenodo.23202152 .
